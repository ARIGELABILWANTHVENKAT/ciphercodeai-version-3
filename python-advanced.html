    Module 1

    Iterators and generators

    Understand the protocol behind every for loop, then use generators to process unlimited data in constant memory.

    About 70 minutes

    Every for loop you have ever written relies on a small, precise contract called the iterator protocol. Once you know that contract, generators, lazy pipelines, zip, enumerate, file reading and database cursors all stop being separate tricks and become one idea seen from different angles. This idea is also what lets a Python program handle a 50 GB log file on a laptop with 8 GB of RAM.

    What a for loop really does

    When Python meets for item in thing:, it does two things. First it calls iter(thing), which returns an iterator. Then it calls next(iterator) again and again, assigning each result to item, until next raises StopIteration. That exception is not an error here; it is the signal that says “no more values”, and the loop swallows it quietly. You can run the same steps by hand:

    Iterable versus iterator

    These two words are used loosely, and mixing them up causes real bugs. The difference is small but important:

    TermMust implementRemembers position?Examples
    Iterable__iter__() returning an iteratorNolist, tuple, str, dict, set, range, file objects
    Iterator__next__() and __iter__() returning itselfYesiter(list), generators, zip(), map(), open() file objects

    An iterable can be looped over many times because each iter() call gives a fresh iterator. An iterator can only be used once: when it is exhausted, it stays exhausted. That is why you can loop over a list forever but only once over a zip object.

    Building an iterator by hand

    To create your own iterator, write a class with __iter__ and __next__. Walk through the example below line by line. __init__ stores the starting state. __iter__ returns self, because an iterator is its own iterable. __next__ checks whether there is anything left; if not it raises StopIteration; otherwise it produces the current value and updates the state for next time.

    Generators: iterators without the boilerplate

    Writing a class for every iterator is tedious, so Python gives you a shortcut. Any function that contains the keyword yield becomes a generator function. Calling it does not run the body. It returns a generator object, which is a ready-made iterator. Each next() call runs the body until the next yield, hands that value out, and freezes the function exactly where it is, including all local variables. The next call thaws it and carries on from that line.

    Why laziness matters
    A list holds every value in memory at once. A generator holds one value plus its own small frame, no matter how many values it will eventually produce. That turns memory use from “proportional to the data size” into “constant”. It also lets you work with infinite sequences, such as a stream of sensor readings, because you only compute what you actually ask for.

    Generator expressions and the memory difference

    A list comprehension uses square brackets and builds the whole list immediately. Swap the brackets for parentheses and you get a generator expression, which builds nothing until you iterate it. When you only need to consume the values once, for example inside sum(), max(), any() or ",".join(), a generator expression is the better choice. You can even drop the extra parentheses when it is the only argument: sum(n * n for n in data).

    Lazy pipelines: the real payoff

    The most powerful use of generators is chaining them into a pipeline, like stations on a factory line. Each stage takes an iterator in and yields an iterator out. Because every stage is lazy, the first record travels the whole pipeline before the second record is even read. Nothing is ever held in bulk. Here is a tiny log processor with three stages. Notice how each function does exactly one job, so you can test, reorder or replace stages independently.

    yield from, send() and close()

    yield from other hands control to another iterable and passes every value it produces straight out to your caller. It replaces a for x in other: yield x loop and also forwards send(), throw() and return values correctly. It is ideal for recursion, such as walking a directory tree.

    Generators can also receive values. The expression value = yield result hands result out and, when someone calls gen.send(x), resumes with value set to x. You must “prime” such a generator with one next() call first, to advance it to the first yield. Finally, gen.close() raises GeneratorExit at the paused yield so that any finally block inside gets to run.

    Generators are single-use
    A generator cannot be rewound. After you loop over it once, a second loop sees nothing and raises no error, so the bug is silent. If you need the data twice, either call the generator function again to make a fresh generator, or convert to a list with list(gen) when the data fits in memory. Also remember that len(gen) and gen[0] do not work: TypeError: object of type 'generator' has no len() and TypeError: 'generator' object is not subscriptable.

    Common errors and how to read them

    • TypeError: 'int' object is not iterable: you passed a number where an iterable was needed, for example for i in 5. You probably meant range(5).
    • TypeError: can't send non-None value to a just-started generator: you called send(value) before priming. Call next(gen) first.
    • RuntimeError: generator raised StopIteration: since Python 3.7, a stray StopIteration escaping from inside a generator body is turned into a RuntimeError (PEP 479). End a generator with return, never by raising StopIteration yourself.
    • An empty result on the second pass: the generator was already exhausted. Create a new one.

    When not to use a generator

    Generators trade convenience for restrictions. Use a plain list when you need random access, the length, several passes over the same data, or slicing. Use a list when the data is small, because the clarity is worth more than the saved bytes. And remember that errors inside a lazy pipeline surface late: a bad line may only blow up when the consumer reaches it, far from where the pipeline was built. That is the price of laziness, and it is usually worth paying for large or streaming data.

    Remember this

    • A for loop calls iter() once, then next() repeatedly until StopIteration.
    • An iterable produces fresh iterators; an iterator remembers its position and is single-use.
    • A function containing yield returns a generator; its body only runs when you call next().
    • Generator expressions and pipelines keep memory flat, no matter how large the data.
    • yield from delegates to a sub-iterator; send() and close() let you talk to a running generator.

    Module 2

    Decorators and closures

    Learn how functions can capture state and wrap other functions, then build the logging, retry, registry and caching decorators used in real codebases.

    About 75 minutes

    You have probably typed @something above a function many times: @property, @staticmethod, @app.route(...), @pytest.fixture. A decorator looks like magic until you see that it is built from just three ordinary ideas: functions are objects, functions can be defined inside other functions, and inner functions can remember variables from the function that created them. That last idea is called a closure, and it is where we start.

    Closures: functions that remember

    When an inner function uses a variable from its enclosing function, Python keeps that variable alive in a small storage box called a cell, even after the outer function has returned. The inner function carries the cell with it. In the example below, make_counter finishes running immediately, yet hits still remembers count. Each call to make_counter creates a brand-new, independent cell, so hits and other do not interfere.

    One detail: assigning to a captured variable would normally create a new local variable. To say “I mean the outer one”, declare it with nonlocal. Reading a captured variable needs no declaration.

    A decorator is a function that takes a function and returns a function

    Now combine closures with the idea that functions are values. A decorator receives a function, defines a wrapper function that adds behaviour around the call, and returns the wrapper. The line @log_calls above def apply_discount is nothing but shorthand for apply_discount = log_calls(apply_discount) executed right after the function is defined.

    Look at the structure in the example: the wrapper accepts *args, **kwargs so it works for any function signature, calls the original, and returns its result. Forgetting that final return is the number one decorator bug, because the decorated function would then always return None.

    Always use functools.wraps
    Without it, every decorated function pretends to be called wrapper with no docstring. Stack traces become confusing, help() becomes useless, and frameworks that look up functions by name (such as Flask endpoints) can collide with AssertionError: View function mapping is overwriting an existing endpoint function: wrapper.

    Decorators that take arguments

    To write @retry(times=3), you need one more layer. retry(times=3) is a normal call that returns the actual decorator, and that decorator is then applied to your function. So there are three nested levels: the factory receives the settings, the decorator receives the function, and the wrapper receives the call arguments. The wrapper uses closures to read times and exceptions from the outermost level.

    Stacking order

    You can apply several decorators to one function. They are applied from the bottom up (the one closest to def wraps first), but when the function is called, execution flows from the top down (the outermost wrapper runs first). Think of wrapping a gift: the inner paper goes on first, but the recipient unwraps the outer layer first.

    Decorators you get for free in functools

    functools.lru_cache remembers the results of a function for each distinct set of arguments, a technique called memoisation. It turns exponential recursion into linear work. The arguments must be hashable, and the function should be pure (the same input always gives the same output with no side effects), otherwise you cache stale or wrong answers. functools.cache (Python 3.9+) is the same thing with no size limit. functools.singledispatch lets one function name behave differently depending on the type of its first argument, replacing long isinstance chains.

    Why decorators exist
    They separate what a function does from cross-cutting concerns such as logging, timing, retries, permission checks and caching. Without decorators, you would paste the same ten lines into fifty functions and fix the same bug fifty times. With them, the concern lives in one place and is applied with one line.

    Trade-offs and common mistakes

    • Forgetting parentheses: @retry instead of @retry() passes the function as times. The result is a confusing TypeError later. If your decorator takes arguments, always call it, even with none.
    • Hidden behaviour: too many stacked decorators make it hard to tell what a call actually does. Keep stacks short and document their order.
    • Caching impure functions: lru_cache on a function that reads a file or the clock returns stale data forever. Cache only pure functions, or clear with fib.cache_clear().
    • Methods and lru_cache: the cache holds a reference to self, which can keep objects alive and leak memory. Prefer caching module-level functions.
    • Debuggability: if you see an error inside wrapper, look one frame up the traceback to find your real function.

    Remember this

    • A closure is an inner function that keeps the variables it uses alive after the outer function returns.
    • @decorator above def f means f = decorator(f); the wrapper should accept *args, **kwargs and return the result.
    • Always add @functools.wraps(func) so name, docstring and metadata survive.
    • A decorator with arguments has three levels: factory, decorator, wrapper.
    • Stacked decorators wrap bottom-up but execute top-down; use lru_cache only on pure functions.

    Two decorators are stacked: @a on top of @b on top of def f. Which is applied to f first?

    Module 3

    Context managers and resource safety

    Guarantee that files, locks, connections and transactions are always cleaned up, even when your code crashes halfway through.

    About 60 minutes

    Programs constantly borrow things: open files, database connections, network sockets, locks, temporary directories. Every borrowed thing must be given back, even if an exception is thrown in the middle. If you forget, files stay open, locks stay held and your service slowly runs out of file handles. The with statement is Python's answer, and the machinery behind it is called the context manager protocol.

    The problem with manual cleanup

    The naive pattern is f = open(path), work with it, then f.close(). If anything between those lines raises an exception, the close() never runs. The fix is try/finally, because finally always executes. It works but is noisy, easy to forget, and has to be repeated everywhere. A context manager packages the “set up, then always tear down” pair into one reusable object, and with applies it in a single readable line.

    The protocol: __enter__ and __exit__

    An object is a context manager if it has two methods. __enter__(self) runs when the block starts; whatever it returns is bound to the name after as. __exit__(self, exc_type, exc, tb) runs when the block ends for any reason. If the block finished normally, all three arguments are None. If an exception escaped, they describe it. The return value of __exit__ matters: return a true value and the exception is swallowed; return false (or nothing) and it continues to propagate. Walk through this example and match each printed line to the method that produced it.

    What with really expands to
    with M() as x: body behaves like: call __enter__; run body inside a try; on an exception, call __exit__(type, value, traceback) and re-raise unless it returns true; otherwise call __exit__(None, None, None). It is try/finally with the boilerplate written once, correctly, by the author of the class.

    Swallowing exceptions on purpose

    Sometimes an error is expected and harmless, such as deleting a file that may already be gone. Writing try/except/pass works, but contextlib.suppress says your intent more clearly: “these specific errors are fine here”. Name only the exceptions you truly expect. Suppressing Exception broadly hides real bugs.

    Writing context managers with @contextmanager

    Writing a class with two methods is fine, but for most cases a generator is shorter. Decorate a generator function that has exactly one yield with @contextmanager. Everything before the yield is the setup (__enter__). The yielded value becomes the as variable. Everything after the yield is the teardown (__exit__). If the body raises an exception, it is thrown into the generator at the yield line, so you can catch it with try/except around the yield.

    The example below implements a tiny transaction: it snapshots a dictionary, lets the block modify it, and if anything fails it restores the snapshot. This all-or-nothing behaviour is exactly how database transactions work, and the same shape is used for commit() and rollback() in real database libraries.

    Put cleanup in finally
    In a @contextmanager function, an exception in the body is raised at the yield. If your teardown code sits after the yield without try/finally, it is skipped whenever the body fails. Use try: yield ... finally: cleanup() for resources that must always be released. Other errors you may meet: RuntimeError: generator didn't yield (the generator never reached a yield), and TypeError: 'X' object does not support the context manager protocol (you used with on something lacking __enter__/__exit__).

    Several resources at once with ExitStack

    Stacking with a, b, c: works when you know the count in advance. When the number of resources is only known at run time, for example “open every file in this list”, use contextlib.ExitStack. You register each context manager with enter_context, and when the block ends the stack closes everything in reverse order (last opened, first closed), even if one of the closings fails. That reverse order mirrors how you would unpack a stack of boxes.

    A reusable utility: temporary environment variables

    Context managers shine for “change something temporarily, then restore it”. Tests that need a particular environment variable, scripts that temporarily change the working directory, and code that swaps a setting for one operation all fit. The pattern is always: save the old value, change it, yield, restore in finally.

    Where you will meet context managers

    • open() for files, and tempfile.TemporaryDirectory() for scratch space that disappears afterwards.
    • threading.Lock(): with lock: acquires and always releases, avoiding deadlocks caused by a forgotten release().
    • Database libraries: with connection: typically commits on success and rolls back on error.
    • async with is the same idea for coroutines, using __aenter__ and __aexit__; you will use it in the asyncio module.

    When not to use one: if there is no cleanup and no paired setup, a context manager adds ceremony without value. Use a plain function. And do not keep a resource open beyond its block by smuggling the as variable out: a file object used after its with block raises ValueError: I/O operation on closed file.

    Remember this

    • with guarantees teardown by calling __exit__ whether the block succeeds or raises.
    • __enter__ returns the value for 'as'; a true return from __exit__ swallows the exception.
    • @contextmanager turns a generator with one yield into a context manager; wrap the yield in try/finally.
    • suppress() ignores only the exceptions you name; ExitStack handles a run-time number of resources.
    • The shape 'save, change, yield, restore' fits transactions, temporary settings and locks.

    Module 4

    Threads and processes

    Do more than one thing at a time: know when threads help, when only processes will do, and why the GIL changes the answer.

    About 60 minutes

    A program that waits is wasting time. While your code waits for a web server to reply, a disk to deliver bytes or a database to answer, the CPU sits idle. Concurrency means arranging your program so that other useful work happens during those gaps, or so that several CPU cores work at once. Python gives you three tools: threads, processes and asyncio. This module covers the first two. The next module covers asyncio. Choosing correctly starts with one question: what is my program waiting for?

    I/O-bound or CPU-bound?

    A task is I/O-bound when most of its time is spent waiting for something outside your code: a network response, a file read, a sleep. Doubling the CPU speed would not help it, because the CPU is not the bottleneck. A task is CPU-bound when it spends its time calculating: parsing a huge file, resizing images, checking primes, training a model. For these tasks the only cure is more cores doing calculations at the same moment, or a faster algorithm. Everything else in this module follows from that split.

    QuestionI/O-bound workCPU-bound work
    ExampleDownload 50 web pagesCount primes below 10 million
    What is the program doing most of the time?WaitingCalculating
    Do threads help in standard CPython?Yes, stronglyNo, because of the GIL
    Do processes help?Yes, but heavier than neededYes, this is their job

    Threads and the problem of shared state

    A thread is an independent line of execution inside your process. All threads share the same memory, which is both their strength (passing data is easy) and their danger (two threads can touch the same variable at once). You create one with threading.Thread(target=function), begin it with start() and wait for it to finish with join().

    The classic danger is the race condition. Incrementing a counter looks like one step, but it is really three: read the value, add one, write it back. If two threads both read the old value before either writes, one increment is lost. Real races depend on tiny timing differences, so they are hard to reproduce. The example below forces the unlucky timing with a Barrier (a meeting point where both threads must arrive before either continues) so that the bug appears every single time. Then it shows the fix: a Lock, used with with so it is always released.

    Race conditions do not crash
    A race condition never raises an error. It silently produces wrong numbers, and only sometimes. A test that passes ten times proves nothing. Treat any variable that several threads write to as dangerous until it is guarded by a lock, or better, until you stop sharing it: give each thread its own data and combine the results at the end. Two other classic mistakes are forgetting join() (the main program may finish before the threads do) and a deadlock, where thread A holds lock 1 waiting for lock 2 while thread B holds lock 2 waiting for lock 1, so nothing ever moves again. Always acquire multiple locks in the same order everywhere.

    A worker pool with queue.Queue

    Starting one thread per task does not scale: ten thousand tasks would mean ten thousand threads. The standard pattern is a small fixed group of worker threads that pull jobs from a shared queue.Queue. The queue is already thread-safe, so you do not need your own lock around put() and get(). Workers loop forever taking jobs, and you stop them by putting one sentinel value (here None) per worker. jobs.join() blocks until every job has been marked finished with task_done().

    The GIL, explained honestly

    CPython, the standard Python, has a Global Interpreter Lock (GIL): a lock that lets only one thread run Python bytecode at a time. It exists because CPython manages memory with reference counting, and making every count update thread-safe individually would be slow and complex. The GIL is a simple, fast solution for single-threaded code, and it protects the interpreter's internals. It does not protect your own variables, which is why the race condition above still happens.

    The consequences are precise. When a thread does I/O (reads a socket, waits on time.sleep, reads a file), it releases the GIL while it waits, so other threads run. Threads therefore speed up I/O-bound programs very well. When threads do CPU-bound Python work, they take turns holding the GIL, so four threads give you roughly the speed of one, sometimes slightly worse because of switching. Some C extensions such as NumPy release the GIL during heavy calculations, which is why they can use several cores from threads.

    Why not simply remove the GIL?
    Removing it makes single-threaded programs slower and breaks C extensions that assume it exists. Python 3.13 introduced an experimental free-threaded build (often named python3.13t) where the GIL can be turned off, and the ecosystem is still adapting. Treat it as a development to watch, not as something to depend on yet. The rules in this module remain the safe default for standard Python.

    concurrent.futures: the comfortable interface

    Managing threads and queues by hand is educational but rarely necessary. The concurrent.futures module gives you pools with one shared interface. pool.map(function, items) runs the function on every item and yields the results in input order. pool.submit(function, arg) returns a Future, an object representing a result that is not ready yet; future.result() waits for it and, importantly, re-raises any exception the worker hit. The with block waits for all work to finish before leaving.

    Processes for CPU-bound work

    A process is a separate copy of the interpreter with its own memory and its own GIL, so processes truly run in parallel on different cores. The price is overhead: starting a process is slower than starting a thread, and data cannot be shared directly. It has to be pickled (converted to bytes), sent to the worker and unpickled. ProcessPoolExecutor has the same interface as the thread version, so switching is often a one-word change.

    There is one rule you must follow: wrap the starting code in if __name__ == "__main__":. On Windows and macOS, child processes are started by importing your script afresh. Without the guard, every child would run the pool-creating code again and spawn more children. Python detects this and stops it with RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase.

    Because arguments and results travel by pickle, only picklable things can cross the boundary. Top-level functions and ordinary data are fine. Lambdas, locally defined functions, open files, locks and database connections are not. The error you will meet is _pickle.PicklingError: Can't pickle <function <lambda> ...> or AttributeError: Can't pickle local object. The fix is to move the function to the top level of a module.

    Choosing between them

    • Waiting on network, disk or a database, and the work per item is small: ThreadPoolExecutor. It is light and simple. For thousands of connections, consider asyncio (next module).
    • Heavy calculation in pure Python: ProcessPoolExecutor, sized to your core count (os.cpu_count()). Make each task big enough that the pickling cost is small by comparison.
    • Heavy calculation inside NumPy or another library that releases the GIL: threads may already be enough. Measure first.
    • Neither: if a task takes 20 ms in total, concurrency adds complexity for no gain. A better algorithm usually beats more workers.

    Remember this

    • Ask first: is the task I/O-bound (waiting) or CPU-bound (calculating)? The answer picks the tool.
    • Threads share memory, so any variable several threads write to needs a Lock, or should not be shared at all.
    • The GIL lets one thread run Python bytecode at a time: threads help I/O-bound work but not CPU-bound pure Python.
    • concurrent.futures gives threads and processes one interface; map keeps input order and result() re-raises worker errors.
    • Process pools need the if __name__ == '__main__' guard and picklable functions and data.

    Why do four threads running a pure-Python CPU-bound loop give roughly the speed of one thread in standard CPython?

    The Global Interpreter Lock serialises bytecode execution. Threads take turns, so CPU-bound pure Python does not run in parallel. Processes each have their own GIL.

    What does a Lock protect you from?

    A lock lets one thread at a time into a critical section, so a read-modify-write such as counter += 1 cannot be interleaved and lose an update.

    Why is the if __name__ == '__main__' guard required when using ProcessPoolExecutor on Windows and macOS?

    With the spawn start method, each child process imports the main module. Unguarded pool creation would run again in every child, which Python stops with a RuntimeError about the bootstrapping phase.

    Module 5

    Asyncio: thousands of waits on one thread

    Write programs that juggle thousands of slow network calls on a single thread, and learn the one mistake that freezes all of them at once.

    About 60 minutes

    Threads are one way to wait for many things at once. asyncio is another, and it works on a different idea: cooperative multitasking. Your whole program runs on one thread. A piece of code called the event loop keeps a list of jobs. It runs one job until that job says "I am going to wait for something, someone else can have a turn", then it picks the next job. Nothing is ever interrupted in the middle of a line, so there are no lost updates and far fewer locks. The price is that every job must volunteer to pause.

    Think of one chef cooking five dishes. The chef never stands and stares at a pot of rice. They put it on, switch to chopping, come back when the timer rings. One person, five dishes, no extra kitchens. That is asyncio. It shines when you wait on the network or disk for a long time and have many things in flight: web crawlers, chat servers, API gateways, anything that calls other services.

    Coroutines and await

    A function defined with async def is a coroutine function. Calling it does not run its body. It returns a coroutine object, a paused job waiting for the event loop. You run it in one of two ways: hand it to asyncio.run() from ordinary code, or write await in front of it from inside another coroutine. The word await means two things at once: start this job and wait for its result, and while I wait, the loop may run other jobs. Those are the only places where switching can happen, so you can read an async function and see every possible pause point.

    The first example shows both facts. Calling greet() gives a coroutine object. Then the second half compares awaiting three jobs one after another with starting them together using asyncio.gather(). The sleeps are tiny so the script finishes quickly, but the pattern is exactly what you would use with real network calls.

    Forgetting await is silent
    Writing fetch("a", 1) without await creates a coroutine object and throws it away. Nothing runs, and your only clue is a warning on stderr: RuntimeWarning: coroutine 'fetch' was never awaited. If an async function seems to do nothing, check every call to it for a missing await. Also remember that asyncio.run() must not be called from inside a running loop (notebooks such as Jupyter already have one; there you simply write await main()).

    Tasks: starting work without waiting for it

    await job() runs a job and waits right there. Sometimes you want to start a job, carry on with other work, and collect the result later. asyncio.create_task(job()) wraps the coroutine in a Task and schedules it on the loop immediately. The task begins running the next time your current code reaches an await. You can then await the task later to get its result, or call task.cancel() to stop it. gather() creates tasks for you behind the scenes.

    To see switching happen, the next example uses await asyncio.sleep(0). Sleeping for zero seconds does no waiting at all. It simply says "let someone else have a turn", which makes the interleaving visible and perfectly repeatable.

    Timeouts, errors and cancellation

    Network calls hang. Always put a limit on them. asyncio.wait_for(job, timeout=seconds) cancels the job and raises asyncio.TimeoutError if it takes too long. Python 3.11 added the nicer async with asyncio.timeout(seconds): block that limits everything inside it. Cancellation works by raising asyncio.CancelledError inside the job at its current await, so try/finally blocks in the job still run and clean up. Never swallow CancelledError with a bare except.

    Errors need a decision. By default gather() raises the first exception and leaves the other jobs running unobserved. If you would rather collect everything, pass return_exceptions=True: failures come back as exception objects in the results list, in order, and you check each one.

    TaskGroup: structured concurrency (Python 3.11+)

    gather has an awkward weakness: if one job fails, the others keep running with nobody watching them. Python 3.11 added asyncio.TaskGroup, which follows the rule of structured concurrency: every job started inside the async with block must finish before the block ends, and if any job fails, the rest are cancelled. Failures arrive together as an ExceptionGroup, which you catch with except*. This is the recommended style on modern Python. The example below needs 3.11 or newer, so its output is shown as a recorded run.

    Limiting concurrency with a semaphore

    Starting 10,000 downloads at once will exhaust file handles, overwhelm the server and get you rate-limited. An asyncio.Semaphore(n) is a counter of permits. async with sem: takes a permit, waiting if none are left, and returns it when the block ends. At most n jobs are inside the block at once, however many tasks you created.

    The blocking-call trap

    Here is the rule that matters most: one slow synchronous call freezes every job on the loop. The event loop only regains control at an await. If you call time.sleep(5), requests.get(...), a big file read or a heavy calculation, the loop is stuck inside it, and your thousand other connections get no service for five seconds. Use async versions (asyncio.sleep, httpx or aiohttp instead of requests), or push the blocking work to a thread with asyncio.to_thread() (Python 3.9+) so the loop stays free. For heavy CPU work, use a process pool; asyncio does nothing for CPU-bound code.

    Why is await explicit?
    Some languages switch jobs invisibly. Python makes you write await at every pause point on purpose. Because switches can only happen at those marked places, code between two awaits is effectively atomic: no other job can touch your variables halfway through. That is why the active += 1 lines above need no lock. The cost of that guarantee is the trap above: the loop cannot take control back from code that never awaits.

    Async, threads or processes?

    SituationBest toolReason
    Thousands of network calls, libraries with async supportasyncioCheapest per connection; no locks needed between awaits
    A few dozen blocking calls, library has no async versionThreads (ThreadPoolExecutor)Simple, and the GIL is released while waiting on I/O
    Heavy calculation on many coresProcesses (ProcessPoolExecutor)Each process has its own GIL

    Async has a cost: it spreads. Once one function awaits, its caller must be async too, and so on up to asyncio.run(). Mixing async and blocking libraries is where most real-world bugs come from, so pick one style per program and keep the boundary clear.

    Remember this

    • Calling an async def function returns a coroutine; nothing runs until you await it, schedule it as a task, or pass it to asyncio.run().
    • await is the only place the loop can switch jobs. gather() and create_task() let waits overlap, so total time is the slowest job, not the sum.
    • Always bound slow calls with a timeout and bound parallelism with a Semaphore.
    • Prefer TaskGroup (3.11+) for structured concurrency; use return_exceptions=True with gather when you want every outcome.
    • A blocking call inside a coroutine freezes the whole loop. Use async libraries, or asyncio.to_thread() for blocking work.
    • asyncio helps with waiting, not calculating. CPU-bound work still needs processes.

    Module 6

    Typing and data modelling

    Describe your data precisely with type hints, generics, protocols, dataclasses and enums, then let tools catch mistakes before your users do.

    About 60 minutes

    Python is dynamically typed: a variable can hold a number now and a string a moment later, and nothing complains until a line actually fails at run time. That freedom is wonderful for a ten-line script and painful for a ten-thousand-line codebase, where the question "what does this function expect, and what does it give back?" decides whether a change is safe. Type hints answer that question in the code itself. They are labels you attach to parameters, return values and variables. Python stores them but does not enforce them. Their readers are your teammates, your editor, and a separate program called a type checker (mypy, pyright) that reads your code without running it and reports contradictions.

    Hints in practice

    Annotate a parameter with a colon (prices: list[float]) and a return value with an arrow (-> float). Since Python 3.9 you can write built-in container types directly, list[int], dict[str, float], tuple[int, str], and since 3.10 you can write a choice between types with a pipe: int | None means "an integer or nothing". Older code imports List, Dict and Optional from typing; you will see both styles, and the modern one is shorter.

    Why does Python not enforce its own hints?
    Python uses gradual typing. You can add hints to the parts of a program where they pay off and leave the rest alone, and old untyped code keeps working. If hints were enforced at run time, every call would pay a checking cost and every existing library would break. Instead the checking happens ahead of time, in your editor and your continuous-integration pipeline, where mistakes are cheapest to fix.

    Generics: one definition, many types

    Suppose you write first(items) that returns the first element. If you hint the result as int it is wrong for a list of strings, and if you hint it as object the caller loses all information. A type variable solves this: T = TypeVar("T") stands for "whatever type the caller uses", and the same T appearing in the input and output links them. A class can be generic in the same way by inheriting from Generic[T]. Python 3.12 added a shorter syntax (class Stack[T]:), but the form below works on every supported version.

    Protocols and TypedDict: describing shape instead of ancestry

    Python programmers rely on duck typing: if it has a send() method, treat it as a notifier. A typing.Protocol lets you write that expectation down. A class matches a protocol simply by having the right methods; it does not have to inherit from anything. This is called structural typing, and it keeps modules decoupled: your function can accept any object with the right shape, including classes from libraries you do not control. Add @runtime_checkable and you can also use isinstance, which checks that the method names exist (not their signatures).

    Real programs also pass dictionaries around, such as JSON from an API. A TypedDict describes which keys a dictionary has and what each value is, so a checker can catch a misspelled key. At run time it is a perfectly ordinary dict.

    Dataclasses and enums: modelling your domain

    Writing __init__, __repr__ and __eq__ by hand for every record class is tedious. @dataclass generates them from annotated fields. The options worth knowing: frozen=True makes instances immutable (and hashable), order=True adds comparison methods, slots=True (3.10+) saves memory and blocks accidental new attributes, and kw_only=True (3.10+) forces keyword arguments. For mutable defaults such as lists you must use field(default_factory=list). Validation goes in __post_init__, which runs right after the generated __init__.

    An Enum is a fixed set of named values. Instead of the string "shipped" that might be mistyped as "shiped" in one place, you write Status.SHIPPED, and a typo becomes an immediate AttributeError and a checker error. Use auto() when the actual values do not matter, and IntEnum when members must also behave as integers (for sorting by priority, say).

    Mutable defaults and the Any escape hatch
    Writing items: list[Item] = [] in a dataclass is refused with ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory. That is Python protecting you from one list shared by every instance. Use field(default_factory=list). The second trap is Any: a value typed Any switches checking off for everything it touches, and the silence spreads. Prefer a precise type, a Protocol or object, and use # type: ignore[code] sparingly with the error code and a comment saying why.

    The mypy mindset

    A type checker is a tireless reviewer that reads every line without running it. Install it with pip install mypy and run mypy yourfile.py. Start with the defaults on new files, and as the code matures turn on --strict (or strict = true in pyproject.toml) so missing annotations and loose types are reported. Run the checker in your continuous-integration pipeline next to your tests: tests prove that the cases you thought of work; the checker proves that whole classes of mistakes cannot happen anywhere. Annotate the boundaries first: public functions, data models and anything that crosses a module line. Inside a small function, the checker infers types well on its own.

    Pydantic: validation at the edge

    Hints do not stop bad data arriving from a web form, a JSON file or an environment variable, because that data appears at run time. Pydantic is a third-party library (pip install pydantic) that turns annotated classes into validators: it checks and converts incoming data, and raises a detailed error when it cannot. Many modern frameworks, FastAPI among them, are built on it. A good split is: plain dataclasses for trusted data inside your program, Pydantic models where data enters from outside.     Remember this

    • Type hints are labels for humans and tools. Python stores them but does not enforce them at run time.
    • Use TypeVar and Generic so one function or class works for many types while keeping input and output linked.
    • Protocol describes the shape an object must have, and TypedDict describes the keys of a dict, with no inheritance needed.
    • Dataclasses remove boilerplate (frozen, slots, order, default_factory, __post_init__); Enums replace magic strings with named members.
    • Run a checker such as mypy in CI, start by annotating public boundaries, and avoid Any.
    • Validate untrusted data at the edge with a library like Pydantic; use plain dataclasses inside.

    What does Python do at run time if you call a function annotated (x: int) with a string?

    Annotations are stored but ignored by the interpreter. A separate type checker such as mypy, or a validation library such as Pydantic, is what catches the mismatch.

    How does a class satisfy a typing.Protocol?

    Protocols use structural typing: matching by shape. Any class with a compatible send() method counts as a Notifier, with no inheritance required.

    Why does a dataclass reject the field items: list[Item] = [] ?

    A default value is created once and reused. A shared mutable list would leak data between instances, so dataclasses raise ValueError and ask for default_factory, which builds a new list each time.

    Module 7

    Performance and profiling

    Learn to measure before you optimise, find the real bottleneck with timeit and cProfile, and pick data structures, caching and memory techniques that make Python code fast for the right reasons.

    About 60 minutes

    Most slow Python programs are slow in one or two places, and those places are almost never where the author guessed. A developer who spends a day rewriting a loop that takes 2% of the run time has made the code harder to read and the program no faster. Performance work is therefore a loop of its own: measure, find the bottleneck, change one thing, measure again. This module gives you the tools for each step and the knowledge to choose the change that actually helps.

    Why guessing fails

    Python hides a lot of work behind short lines. A single x in items may scan a million entries, and a single += on a string may copy the whole string. Your intuition about cost comes from how the code looks, but the machine pays for what the code does. A profiler reports what it does, so it wins every argument against intuition.

    Step 1: time small pieces with timeit

    The timeit module runs a snippet many times and reports the total seconds. It turns off garbage collection during the run and uses the best available clock, which removes much of the noise you get from wrapping code in time.time() calls. Use it to compare two small alternatives. Take the minimum of several repeats rather than the average, because slowdowns come from other programs on your machine, never from your code running unusually fast.

    The example below shows the shape of a measurement. It deliberately prints no timings, because timings differ on every computer. It prints facts about the result instead. When you run it yourself, print min(times) and compare the two numbers.

    Step 2: find the bottleneck with cProfile

    timeit answers “which of these two is faster?” but not “where does my program spend its time?”. For that you use a profiler. cProfile ships with Python. It records every function call, how many times it happened (ncalls), the time spent inside the function itself (tottime), and the time including everything it called (cumtime).

    Run it on a whole script with python -m cProfile -s cumtime app.py, or around a block of code with cProfile.Profile() and pstats.Stats. Read the output top-down by cumtime to find which of your functions owns the time, then look at tottime inside it to see whether the cost is the function's own work or something it calls. The output below shows the shape for a small log-analysis script. Exact numbers will differ on your machine.

    Profilers change the speed

    A profiler adds overhead to every call, so functions that are called millions of times look worse than they really are. Use the profiler to find where to look, then confirm the improvement with plain timeit or a wall-clock run without the profiler. Also profile realistic data: a profile of ten rows will not show what a million rows do.

    Step 3: choose the right data structure

    The biggest speed-ups usually come from choosing a better algorithm, not from clever tricks. Computer scientists describe growth with Big-O notation: O(1) means the cost stays flat as the data grows, O(n) means it grows in step with the data, and O(n^2) means doubling the data quadruples the work. Testing x in some_list is O(n) because Python may check every element, while x in some_set and key in some_dict are O(1) on average because they use hashing.

    If a loop contains if x in big_list, converting big_list to a set once, outside the loop, often turns a minutes-long job into a seconds-long one. Build the set once. Do not rebuild it inside the loop.

    Step 4: save memory and repeated work

    Speed and memory are linked, because creating huge objects takes time too. A generator expression produces values one at a time instead of building a full list, so it uses almost constant memory. __slots__ tells a class not to create a per-instance __dict__, which saves memory when you create hundreds of thousands of small objects. functools.lru_cache stores the results of a pure function so repeated calls with the same arguments cost nothing. And building a large string with repeated += in a loop may copy the growing text each time, so collect pieces in a list and call ''.join(pieces) once.

    Step 5: when pure Python is not enough

    Sometimes the algorithm is right and the loop is still too slow, because CPython executes one bytecode instruction at a time. The cure is to move the hot loop out of Python. NumPy stores numbers in a compact array and runs the loop in compiled C, so an operation on a million numbers is a single call. numba compiles numeric Python functions to machine code with one decorator. Cython and Rust (through PyO3 and maturin) let you write the hot function in a compiled language and call it from Python. Reach for these last, only for a function the profiler has proven to be the bottleneck, because each one adds a build step and a second language to your project.

    Common performance mistakes
    • Optimising without a profile. You will speed up the wrong code.
    • Caching impure functions. lru_cache on a function that reads the clock or a database returns stale answers.
    • Using __slots__ everywhere. It prevents adding new attributes and complicates inheritance. Use it only for classes with very many instances.
    • Micro-optimising readable code. Saving 3% by turning clear code into a puzzle is a bad trade. A fast program nobody can maintain becomes a slow program next year.
    A performance routine you can reuse
    1. Write a benchmark with realistic data and record the baseline.
    2. Profile it and read the top five rows by cumtime.
    3. Change one thing: a data structure, a cache, a loop moved into NumPy.
    4. Re-run the benchmark. Keep the change only if the number improved enough to matter.
    5. Leave a short comment explaining why the unusual code exists.

    Remember this

    • Measure first: use timeit to compare small alternatives and cProfile to find where the program really spends its time.
    • Better algorithms and data structures beat tricks: sets and dicts for membership, deque for queues, bisect for sorted search, heapq for priorities.
    • Generators, __slots__, lru_cache and ''.join each save memory or repeated work in specific, well-understood situations.
    • Profilers add overhead, so confirm any gain with an ordinary timing and realistic data.
    • Move to NumPy, numba, Cython or Rust only for a proven hot spot, because each adds complexity.

    Module 8

    Descriptors and metaclasses

    Learn the hooks Python uses to look up, set and create attributes and classes, so that properties, methods, dataclasses and ORMs stop feeling like magic.

    About 60 minutes

    Every time you write obj.name Python runs a small, well-defined procedure. Most of the time you never think about it. But @property, methods, @classmethod, __slots__, dataclass fields and every ORM column are all built from the same few hooks, collectively called the data model. This module opens that box. By the end you will know how to write your own validated attribute, intercept missing attributes, shrink objects, react when a subclass is created, and decide when a metaclass is truly necessary (rarely).

    Descriptors: attributes that run code

    A descriptor is an object, stored as a class attribute, that defines at least one of __get__, __set__ or __delete__. When you access an attribute and Python finds a descriptor on the class, it calls the descriptor instead of returning it as plain data. Think of the class attribute as a receptionist: you ask for a value at the desk, and the receptionist decides what to hand over, or whether to refuse your update.

    The three methods have fixed signatures. __get__(self, obj, objtype) runs on read. obj is the instance, or None when the attribute is read from the class itself. __set__(self, obj, value) runs on assignment. __set_name__(self, owner, name) is an optional extra that Python calls once when the class is built, telling the descriptor what name it was given. That saves you from typing the attribute name twice.

    Line-by-line: when the class Ticket is created, Python calls __set_name__ on each Positive it finds, passing 'price' and 'seats'. When __init__ runs self.price = price, Python sees that the class has a descriptor called price with a __set__, so it calls that instead of writing straight to the instance dictionary. The descriptor then stores the real value under _price. Notice that one descriptor object is shared by every Ticket, so it must never keep per-instance data on self. It stores the data on obj.

    Common mistake: storing the value on the descriptor

    Writing self.value = value inside __set__ stores one value for every instance of the class, because there is only one descriptor object. Two tickets would overwrite each other's price. Always store on obj (the instance), as the example does.

    Lookup order: data versus non-data descriptors

    A descriptor with __set__ or __delete__ is a data descriptor. One with only __get__ is a non-data descriptor. The difference decides who wins when the instance also has a value of the same name in its __dict__. Python checks in this order: data descriptors on the class, then the instance __dict__, then non-data descriptors and plain class attributes. Ordinary functions are non-data descriptors. That is exactly how methods work: Class.method.__get__(instance, Class) returns a bound method with self filled in.

    Why Python works this way

    Because methods, properties, classmethod and staticmethod are all descriptors, the language needs just one lookup rule instead of a special case for each feature. The cost is that attribute access is a small search rather than a dictionary read, which is one reason attribute-heavy code can be slower than you expect.

    __getattr__ versus __getattribute__

    These two names look alike and behave very differently. __getattribute__ runs on every attribute lookup. __getattr__ runs only as a fallback, after normal lookup has failed with AttributeError. Use __getattr__ for proxies, lazy attributes and configuration objects. Reach for __getattribute__ only for tracing or very unusual control, and always delegate to super().__getattribute__, otherwise you create infinite recursion.

    Recursion trap in __getattr__

    If __getattr__ reads self._data before _data exists (for example while an object is being copied or unpickled), Python calls __getattr__('_data') again, and again, until RecursionError. Guard it: raise AttributeError immediately for names starting with an underscore, or read through self.__dict__.

    __slots__: fixed attributes, smaller objects

    Normally each instance carries a __dict__, a dictionary of its attributes. That is flexible and costs memory. Declaring __slots__ = ('x', 'y') replaces the dictionary with a fixed array of slots. Objects get smaller and attribute access slightly faster, which matters when you create millions of small objects. The price: you cannot add attributes that were not declared, and weak references and multiple inheritance get fiddlier.

    __init_subclass__, ABCs and plugin registries

    __init_subclass__ is a hook on a parent class that Python calls each time someone subclasses it. It covers most of what people used metaclasses for, in plain code. Pair it with an abstract base class (abc.ABC with @abstractmethod) and you get a plugin registry: subclasses register themselves just by being defined, and Python refuses to create objects from subclasses that forgot a required method.

    Metaclasses: classes that make classes

    Classes are objects too, and something has to create them. By default that something is type. A metaclass is a subclass of type that you plug in with class Thing(metaclass=Meta). Its __new__ runs when the class body is finished, with the class name, its bases and the namespace dictionary, so it can inspect or rewrite the class before it exists. Frameworks such as Django models and SQLAlchemy use this to collect field declarations.

    When to avoid metaclasses

    Try these in order: a plain function, a class decorator, __init_subclass__, a descriptor. Reach for a metaclass only when you must change how the class object itself is created or controlled, such as customising __call__ or __prepare__. Metaclasses also conflict: a class cannot easily combine two unrelated metaclasses, which makes libraries hard to mix. Tim Peters' famous advice applies: if you wonder whether you need one, you do not.

    Remember this

    • A descriptor is a class attribute with __get__, __set__ or __delete__, and one instance is shared by every object, so store data on the instance.
    • Data descriptors beat the instance dictionary, which beats non-data descriptors. Functions and properties are descriptors, which is how methods get self.
    • __getattr__ is a fallback for missing names. __getattribute__ runs on every lookup and must call super() to avoid recursion.
    • __slots__ trades flexibility for smaller, faster objects: no per-instance dictionary and no new attributes.
    • __init_subclass__ plus an ABC gives you plugin registries and early errors without a metaclass. Use a metaclass only when nothing simpler works.

    Check yourself

    Why must a descriptor store per-object data on the instance (obj) rather than on self?

    The descriptor lives on the class, so there is exactly one of it. Anything stored on self is visible to all instances and they would overwrite each other.

    When does __getattr__ run?

    __getattr__ is a fallback. __getattribute__ is the method that runs for every lookup, which is why overriding it carelessly causes infinite recursion.

    Which tool is the best first choice for registering every subclass of a base class automatically?

    __init_subclass__ runs each time the class is subclassed, needs no special class machinery, and mixes safely with other base classes. Metaclasses are the heavier tool.

    Module 9

    Packaging, APIs and production

    Turn your code into something other people can install, call over HTTP, configure safely, observe in production and review with confidence.

    About 65 minutes

    Writing correct code is half of the job. The other half is getting it to run somewhere else, for someone else, and staying understandable when it breaks at 3 a.m. This final module covers the habits that separate a script from a service: packaging, a web API, configuration, logging, containers, automated checks, a few design patterns and a code review checklist. None of it is exotic. All of it is expected of a professional Python developer.

    Packaging with pyproject.toml

    A package is code with a name, a version and declared dependencies, so anyone can run pip install on it. The modern standard is one file, pyproject.toml, which replaces the old setup.py and requirements.txt combination. It holds three things: the build system (which tool turns your folder into an installable file), the project metadata (name, version, Python version, dependencies) and optional tool settings. The recommended layout puts your code in src/yourpackage/, so tests always run against the installed copy and not the loose folder.

    Pin applications, range libraries

    A library that others install should declare wide ranges (fastapi>=0.110) so it can live beside other packages. An application that you deploy should be pinned exactly, with a lock file made by a tool such as pip-tools, uv or poetry, so production builds are repeatable.

    A minimal API with FastAPI

    An API lets other programs use your code over HTTP. FastAPI is a popular framework built on type hints: you describe the shape of a request with a pydantic model and FastAPI validates input, converts types, returns correct status codes and writes interactive documentation for free at /docs. A handler is just a function decorated with the HTTP method and path. Read the example below as three questions: what comes in (Booking), what goes out (a dictionary), and what can go wrong (a 404).

    Do not keep state in module variables in production

    The BOOKINGS dictionary vanishes when the server restarts, and every worker process gets its own copy, so two requests can see different data. It is fine for learning. Real services keep state in a database (PostgreSQL, SQLite with care) or a cache such as Redis.

    Configuration from the environment

    The twelve-factor approach says: configuration that changes between environments belongs in environment variables, not in code. The same build then runs on your laptop, in testing and in production, and secrets such as database passwords never enter your repository. Read them once at startup into a frozen object, convert types there (an environment variable is always a string) and give safe defaults only for non-secret values.

    Structured logging

    print is for you at your desk. Production needs logging: severity levels, a source name and machine-readable output that a log service can search. The best practice is one JSON object per line, with fixed field names and extra context such as a booking id. Then you can ask a tool, "show every ERROR for booking 7", instead of reading text with your eyes. The standard library already does this: write a Formatter that returns JSON and attach it to a handler.

    Containers and automated checks

    A Docker image bundles your code, Python and system libraries into one unit that runs identically everywhere. Order the Dockerfile so that things that change rarely come first: Docker caches each step, so copying pyproject.toml and installing dependencies before copying your source means a code edit does not reinstall everything. Continuous integration (CI) runs your checks on every push so mistakes are caught before a human reviews them. A typical pipeline lints, type checks, runs tests and builds the image.

    Why so much automation?

    Humans are good at judging design and bad at noticing a missing import. Machines are the reverse. Letting CI do the repeatable checks frees code review to focus on the questions only people can answer: is this the right design, and will we understand it in a year?

    Design patterns, the Python way

    Many classic patterns from other languages shrink in Python because functions are objects, modules are singletons and duck typing removes the need for interface hierarchies. Learn the problem each pattern solves, then use the lightest tool that solves it.

    A code review checklist

    Use this list when you review a colleague's pull request, and run through it on your own work before asking for review.

    • Correct: Does it do what the ticket says, including empty input, huge input and failure paths?
    • Tested: Is there a test that would fail without this change? Do tests check behaviour, not implementation details?
    • Readable: Can you explain each function in one sentence? Are names honest? Are there comments for why, not what?
    • Typed and linted: Do ruff and mypy pass? Are public functions annotated?
    • Safe: No secrets in code, no string-built SQL, no unchecked user input, and resources closed with with.
    • Observable: Will a failure leave a useful log line with enough context to diagnose it?
    • Small: Is the change focused enough to review in one sitting? Split unrelated edits into separate pull requests.
