    Module 1

    Functions in depth

    Go beyond def: flexible arguments, functions as values, closures, type hints and the mutable default trap.

    About 55 minutes

    You already know that a function packages a few lines of code under a name. At this level, functions become the main way you shape a program. You will pass them around like data, build small specialised functions out of general ones, and design their inputs so other people (and future you) cannot misuse them by accident.

    The mental model for this whole module: a function is an object. def creates a function object and attaches a name to it, exactly like x = 5 attaches the name x to a number. Once you really believe that, everything below stops feeling like special syntax.

    1. Parameters: positional, keyword and default

    A parameter is the name in the function definition. An argument is the value you pass in the call. Python lets you pass arguments by position (make_order("latte", 2)) or by name (make_order(item="latte", quantity=2)). A parameter with a default value (quantity=1) becomes optional.

    Rules to remember: required parameters must come before parameters with defaults, and once you start using names in a call, every argument after that must also use a name. Python checks this when it reads your code, before anything runs.

    2. *args and **kwargs: accepting any number of arguments

    Sometimes you cannot know how many values will arrive. A café bill might have two items or twenty. Putting * in front of a parameter name tells Python: collect all extra positional arguments into a tuple. Putting ** in front means: collect all extra keyword arguments into a dictionary. The names args and kwargs are only conventions; the stars do the work.

    The stars also work in the opposite direction, at the call site. f(*my_list) unpacks a list into separate positional arguments and f(**my_dict) unpacks a dictionary into keyword arguments.

    Syntax in defWhat it collectsType you receive

    3. Positional-only and keyword-only parameters

    A bare * in the parameter list means everything after me must be passed by name. A / means everything before me must be passed by position. These are design tools. Use keyword-only for options that would be confusing as bare values (book_seat("Asha", 3, True) — true what?). Use positional-only when the parameter name is not meaningful to callers.

    The mutable default argument trap
    Default values are created once, when def runs, not each time you call the function. If the default is a list or dictionary, every call that relies on it shares the same object. This is one of the most famous Python surprises.

    4. Functions are values

    Because a function is an object, you can store it in a variable, put it in a list or dictionary, pass it into another function and return it from one. Functions that take or return other functions are called higher-order functions. You have already used some: sorted(..., key=...) takes a function.

    lambda is a shortcut for writing a tiny, nameless function that is a single expression: lambda p: p * 0.9 means take p, give back p times 0.9. If you need more than one line or want to reuse it with a clear name, use def.

    5. Closures: functions that remember

    When you define a function inside another function, the inner one can use the outer one's variables, even after the outer function has finished. The inner function carries those variables with it. That bundle is called a closure. Picture a coffee token machine: make_counter() builds a machine, and each machine remembers its own count privately.

    Why closures matter
    Closures are the engine behind decorators, callbacks in web frameworks and many testing tools. When you meet @something above a function later, you are looking at a closure at work.

    6. Type hints and docstrings

    A type hint says what kind of value a parameter or return should be: def average(marks: list[float]) -> float. Python does not enforce hints when running. They are documentation that editors and tools like mypy can check, and they make your intent obvious. A docstring is a string literal placed first inside the function. It is stored on the function as __doc__ and shown by help().

    7. Reading the errors you will meet

    Most function mistakes produce a TypeError whose message tells you exactly what is wrong. Learn to read them like a checklist.

    A checklist for designing a function
    Keep it to one job. Give it a verb name (calculate_tax, not tax). Prefer returning a value over printing inside it, so the result can be tested and reused. Use keyword-only parameters for options. Never use a mutable default.

    Remember this

    • A function is an object: store it, pass it and return it.
    • *args collects extra positional arguments into a tuple; **kwargs collects keyword arguments into a dict.
    • Use * to force keyword-only and / to force positional-only parameters.
    • Never use a list or dict as a default value; use None and create it inside.
    • A closure remembers variables from the function that created it; nonlocal lets it change them.
    • Type hints and docstrings document intent but are not enforced at runtime.

    What does <code>def f(*args)</code> give you inside the function?

    *args collects extra positional arguments into a tuple. A dictionary of keyword arguments is what **kwargs gives you.

    Why is <code>def add(item, cart=[])</code> dangerous?

    Module 2

    Comprehensions and iteration

    Write compact loops with comprehensions, and walk data cleanly with enumerate, zip, sorted, any/all and itertools.

    About 55 minutes

    Most programs spend their time looping over data: filtering rows, transforming values, pairing lists, ranking results. Python gives you a toolbox for doing this clearly and in very few lines. Learning it is what makes intermediate code look "Pythonic" instead of like translated C.

    The central idea is iteration. Anything you can put after for ... in is an iterable: lists, strings, dictionaries, files, ranges and more. The tools in this module all accept iterables, so once you learn them they work everywhere.

    1. List comprehensions

    A list comprehension builds a new list in one expression. Read it almost like English: [expression for item in iterable if condition] means give me expression, for each item, but only if condition is true. Compare the long way and the short way for an expense tracker.

    If you want a different value rather than dropping items, use a conditional expression before the for: [x if test else y for x in data]. The position matters. An if at the end filters; an if ... else at the front chooses a value.

    When NOT to use a comprehension
    If it needs more than one condition, nested logic or side effects like print(), write a normal loop. A comprehension that does not fit comfortably on one or two lines is harder to read than the loop it replaced. Also never use a comprehension just for its side effects; [print(x) for x in data] builds a useless list of None.

    2. Dictionary and set comprehensions

    The same idea works with curly braces. {key: value for ...} builds a dictionary and {value for ...} builds a set (which keeps only unique values).

    3. Generator expressions: lazy comprehensions

    Swap the square brackets for round ones and you get a generator expression. It does not build the whole list in memory. It produces one value at a time, only when asked. That is perfect when you only need to feed the values into something like sum(), max() or any().

    4. enumerate and zip

    Beginners often write for i in range(len(items)) to get an index. enumerate does this directly and gives you the index and the item together. zip walks two or more iterables side by side, like the teeth of a zipper, and stops when the shortest one ends.

    5. Sorting with key

    sorted() returns a new sorted list and leaves the original alone; list.sort() sorts in place and returns None (a classic bug is writing x = x.sort()). The key argument takes a function that turns each item into the value to compare by. reverse=True flips the order.

    6. any, all and unpacking

    any(iterable) is true if at least one item is truthy; all(iterable) is true if every item is. With a generator expression they answer yes/no questions about data in one line, and they stop early as soon as the answer is known. Unpacking assigns the parts of a sequence to several names at once, and the starred name *rest soaks up whatever is left over.

    7. itertools: ready-made iteration tools

    The itertools module is a standard-library collection of building blocks. You do not need to memorise it; knowing the five below covers most needs.

    8. The walrus operator, briefly

    The walrus operator := assigns a value and lets you use it in the same expression. It is handy when you would otherwise compute something twice.

    Why this module pays off
    Almost every data task is filter, transform, pair, sort, summarise. These tools express each of those steps in a line, which makes bugs easier to spot. Libraries like pandas copy the same vocabulary, so you will recognise it later.
    Habit to build
    Reach for a plain for loop first when you are unsure. Convert it to a comprehension only when the result is a new collection and the one-liner is easy to read aloud.

    Remember this

    • [expr for x in data if cond] builds a list; use if-else before the for to choose values.
    • Dict and set comprehensions use curly braces; generator expressions use parentheses and are lazy and single-use.
    • enumerate gives index and item; zip pairs iterables and stops at the shortest (strict=True raises instead).
    • sorted returns a new list; list.sort() returns None. Use key= and tuples to sort by several fields.
    • any and all answer yes/no questions in one line; *rest in unpacking collects the leftovers.
    • Sort before groupby, because it only groups neighbouring items.

    Your turn

    Given orders = [('tea', 30), ('latte', 180), ('tea', 30), ('mocha', 210), ('latte', 180)], use comprehensions and one itertools or built-in tool to print: (1) a dictionary of total revenue per drink, (2) a sorted list of unique drink names, and (3) whether any single order is above Rs 200.

    Check yourself

    What is the difference between <code>[x for x in data if x > 0]</code> and <code>[x if x > 0 else 0 for x in data]</code>?

    A trailing if filters items out. An if-else placed before the for chooses a value for every item, so the list length stays the same.

    What does <code>list(zip([1, 2, 3], ['a', 'b']))</code> return?

    zip stops at the shortest input. Only strict=True turns the mismatch into a ValueError.

    Why does <code>itertools.groupby</code> usually need sorted input?

    groupby starts a new group whenever the key changes, so equal keys that are not adjacent end up in separate groups.

    Module 3

    OOP: classes and objects

    Model real-world things as classes: attributes hold data, methods hold behaviour, and each object keeps its own state.

    About 60 minutes

    So far you have kept data in dictionaries and behaviour in separate functions. That works until a program has many kinds of things: bank accounts, library books, students, orders. Passing a dictionary into twenty functions makes it hard to know which function is allowed to do what, and easy to break the data by accident.

    Object-oriented programming (OOP) solves this by bundling data and the functions that work on it into one unit. A class is the blueprint; an object (or instance) is one thing built from it. Think of a class as the architect's plan for a house and each object as an actual house: same plan, but each has its own owner, colour and furniture.

    1. Your first class

    2. Understanding self and __init__

    self is not a keyword. It is simply the conventional name for the first parameter of an instance method, and Python fills it in for you with the object before the dot. Inside a method, self.copies means the copies of this particular book. Without self., you would just create a local variable that disappears when the method ends.

    __init__ is the initialiser. It runs once, right after the object is created, and its job is to set the starting attributes. It does not return anything. Programmers often (loosely) call it the constructor.

    3. Instance attributes vs class attributes

    An instance attribute (set with self.x = ...) belongs to one object. A class attribute (set directly in the class body) is shared by all objects and is good for constants and counters. If you assign to a name through an instance, Python creates a new instance attribute that hides the class one, but it does not change the shared value.

    Mutable class attributes are shared too
    Never write items = [] in the class body expecting each object to get its own list. All objects would append to the same list. Create it in __init__ with self.items = [] instead. This is the class version of the mutable default argument trap.

    4. Making objects printable: __repr__ and __str__

    By default, printing an object shows something unhelpful like <__main__.Book object at 0x7f...>. Two special methods fix this. __str__ returns a friendly string for users and is what print() and str() use. __repr__ returns an unambiguous string for developers, ideally one that looks like the code that rebuilds the object; it is what the console and debuggers show, and it is the fallback if __str__ is missing.

    5. Encapsulation: protecting your data

    Encapsulation means keeping an object's internals behind a controlled doorway so the rest of the program cannot put it into an invalid state. Python is relaxed about this and relies on naming conventions. A single leading underscore (_balance) says internal, please do not touch. A double leading underscore (__balance) triggers name mangling, which renames it to _ClassName__balance to avoid accidental clashes in subclasses. It is not true security, just a stronger hint.

    6. Putting it together: a small design

    A good first design question is: what are the nouns in my problem? Those become classes. What facts does each one know? Those become attributes. What can each one do? Those become methods. A library has Books and Members and a Library that holds them.

    Why bother with classes?
    Each object manages its own state and rules, so bugs stay local. You can add a new kind of thing without rewriting the rest. And the code reads like the problem: library.lend("Godaan") says what it does. Large projects, frameworks like Django and libraries like pandas are built from classes.

    Common errors to recognise

    • TypeError: Book.lend() takes 0 positional arguments but 1 was given — you forgot self in the method definition.
    • AttributeError: 'Book' object has no attribute 'copies' — you never set self.copies in __init__, or misspelled it.
    • TypeError: __init__() missing 1 required positional argument: 'author' — you created the object without every required value.
    • NameError: name 'copies' is not defined inside a method — you wrote copies instead of self.copies.

    Remember this

    • A class is a blueprint; each call like Book(...) makes a separate object with its own attributes.
    • self is the object before the dot; set per-object data with self.name = ... in __init__.
    • Class attributes are shared by all objects; instance attributes belong to one object.
    • Define __repr__ for developers (and __str__ for users) so printing objects is useful.
    • A leading underscore marks an attribute as internal; encapsulation keeps rules in one place.
    • Find classes by looking for nouns in the problem, and methods by looking for verbs.

    Check yourself

    What is <code>self</code> inside a method?

    self is just the conventional name for the first parameter. Python passes the object before the dot into it automatically.

    If you write <code>items = []</code> in a class body, what happens?

    Class-body names are class attributes shared by every instance. Create per-object lists in __init__ with self.items = [].

    Which method should return the string a developer sees in the console and in debuggers?

    __repr__ is the developer-facing representation and is also the fallback when __str__ is not defined.

    Module 4

    OOP: inheritance and dunder methods

    Reuse code with inheritance, choose composition when it fits, and make your objects behave like built-in types.

    About 65 minutes

    A single class is useful. A family of related classes is powerful. In this module you will learn three ideas that make classes feel like part of the language itself: inheritance (a class builds on another), polymorphism (different classes answer the same call in their own way) and dunder methods (special methods that let your objects work with +, ==, len() and sorted()).

    1. Inheritance: is-a relationships

    If a Latte is a kind of Drink, make Latte a subclass (child) of Drink, the superclass (parent). The child automatically gets every attribute and method of the parent, and can add new ones or replace (override) existing ones.

    2. super(): calling the parent

    super() gives you access to the parent class's methods from inside the child. Its most common use is inside __init__: let the parent set up what it knows about, then add your own extras. If you forget to call super().__init__(...), the parent's attributes are never created and you get an AttributeError later.

    3. Polymorphism: one call, many behaviours

    Polymorphism ("many shapes") means you can call the same method on different kinds of objects and each responds in its own way, without the caller needing to know which kind it has. This removes long if type == ... chains.

    4. Composition: has-a relationships

    Inheritance models is-a. Many real relationships are has-a: a car has an engine, a café has a menu. For these, store one object inside another. This is composition. A good rule of thumb is prefer composition: deep inheritance trees become rigid and confusing, while composed objects can be swapped and tested independently.

    The is-a test
    Say the sentence out loud. "A Latte is a Drink" sounds right, so inheritance fits. "A Cafe is a Menu" sounds wrong, but "a Cafe has a Menu" is right, so use composition.

    5. Dunder methods: teaching objects Python's language

    Methods whose names start and end with double underscores ("dunder", short for double underscore) are hooks that Python calls for you. When you write a + b, Python calls a.__add__(b). When you write len(x), it calls x.__len__(). Implement them and your own objects behave like built-ins. You rarely call dunders directly.

    6. @property, @classmethod and @staticmethod

    A property lets you compute a value or validate an assignment while keeping the simple obj.name syntax. You can start with a plain attribute and add a property later without changing any code that uses it. A class method receives the class (cls) instead of an instance, and is the standard way to write alternative constructors. A static method receives neither; it is just a function that lives inside the class for organisation.

    7. Dataclasses: less boilerplate

    Many classes only exist to hold a few fields. Writing __init__, __repr__ and __eq__ by hand for each is repetitive. The @dataclass decorator (standard library, since Python 3.7) writes them for you from type-annotated fields. Use field(default_factory=list) for mutable defaults, and frozen=True to make instances read-only and hashable.

    Common mistakes
    Forgetting super().__init__(); defining __eq__ without __hash__ (objects become unhashable and cannot go in sets or be dictionary keys unless you restore it); returning False instead of NotImplemented for unknown types; and using a property setter name that differs from the getter, which silently creates a second property.
    Why dunder methods are worth learning
    They are the reason sorted(my_objects) and len(my_collection) just work. Every library you will use (pandas, NumPy, Django) relies on them. Understanding them demystifies the "magic" you meet later.

    Remember this

    • Inheritance models is-a; the child inherits attributes and methods and can override them.
    • Call super().__init__(...) in a child so the parent can set up its own attributes.
    • Polymorphism lets one loop call the same method on different classes with no type checks.
    • Prefer composition (has-a) when the relationship is not truly is-a.
    • Dunder methods like __eq__, __lt__, __add__ and __len__ let objects work with Python operators and built-ins.
    • @property, @classmethod, @staticmethod and @dataclass remove boilerplate and add safety.

    Check yourself

    What does <code>super().__init__(name)</code> do inside a child class?

    super() gives access to the parent's methods so the parent can set up the attributes it is responsible for.

    You define <code>__eq__</code> on a class and suddenly its objects cannot be put in a set. Why?

    Equal objects must have equal hashes, so Python sets __hash__ to None unless you define it yourself (or use a frozen dataclass).

    Which relationship is best modelled with composition?

    "Has a" relationships use composition: store one object inside another. The other three are is-a relationships.

    Module 5

    Errors, files and JSON

    Fail on purpose with custom exceptions, then read and write files, JSON and CSV safely with pathlib and logging.

    About 60 minutes

    Real programs meet messy situations: a file that is missing, a user who types letters where a number should be, a saved file that got corrupted. A beginner program crashes. An intermediate program expects these situations, reports them clearly and either recovers or stops cleanly. This module covers the three skills you need for that: designing your own errors, working with files and structured data, and leaving a trail of logs.

    1. Exceptions: a quick, deeper recap

    An exception is an object that Python raises when something goes wrong. It travels up through the functions that called each other until some except block catches it, or until it reaches the top and the program stops with a traceback. The full structure has four parts:

    2. Raising exceptions and writing custom ones

    You can raise errors yourself with raise. This is how a function says "the input you gave me makes no sense". For your own domain, create a custom exception by subclassing Exception. A good name describes the problem (InsufficientFundsError), and a shared base class lets callers catch all errors from your module at once.

    3. Exception chaining: keep the original cause

    Sometimes you catch a low-level error and want to raise a more meaningful one. Use raise NewError(...) from original. Python then shows both in the traceback, with the line "The above exception was the direct cause of the following exception", and stores the original in __cause__. Without from, the traceback says "During handling of the above exception, another exception occurred", which suggests an accident rather than a deliberate translation.

    Mistakes to avoid
    Do not write except: pass; it silences every problem including the ones you needed to see. Do not use exceptions for normal flow when a simple if is clearer. And do not catch an error just to print it and carry on as if nothing happened; either handle it properly, or let it propagate.

    4. Files and with

    A file you open must also be closed, or data may not be fully written and the operating system keeps resources tied up. The with statement guarantees closing even when an error occurs. Always use it. Open modes you need: "r" read (default), "w" write (erases the file first!), "a" append, and add encoding="utf-8" so text such as Hindi or emoji is handled the same on every computer.

    5. pathlib: paths as objects

    The pathlib module treats a path as an object, not a string. You join with /, test with .exists(), and read or write whole text files with one call. It works the same on Windows, macOS and Linux, so you never worry about \ versus /.

    6. JSON: saving structured data

    JSON is a text format for structured data, and the common language of web APIs. It maps neatly to Python: objects become dictionaries, arrays become lists, strings stay strings, numbers stay numbers, true/false/null become True/False/None. The json module has four functions to remember: dumps (Python to string), loads (string to Python), dump (Python to file) and load (file to Python). The trailing s means string.

    7. CSV: rows and columns

    CSV (comma-separated values) stores tables. Never split lines on commas yourself: a value like "Sharma, Asha" contains a comma inside quotes. The csv module handles quoting for you. DictReader and DictWriter use the header row as keys, which makes code self-explanatory. Always open CSV files with newline="".

    8. Logging basics

    print() is fine for results the user should see. For messages about what the program is doing (progress, warnings, failures), use logging. You get severity levels (DEBUG, INFO, WARNING, ERROR, CRITICAL), automatic timestamps if you want them, and the ability to turn noise on or off without editing code. logger.exception() inside an except block records the full traceback.

    Why this matters
    Programs that survive bad input, clearly report what failed and keep their data in standard formats are programs other people can rely on. JSON and CSV also let your code talk to other programs, websites and spreadsheets.
    Putting it together
    A robust pattern: validate input at the edges and raise a custom exception, read and write files with pathlib and with, translate low-level errors with raise ... from, and log what happened. You will use this exact combination in the expense tracker project.

    Remember this

    • try/except/else/finally: catch the narrowest exception, and put cleanup in finally.
    • Custom exceptions subclass Exception; a shared base class lets callers catch a whole family.
    • raise New(...) from original keeps the cause and gives clearer tracebacks.
    • Use with open(...) or pathlib; always pass encoding='utf-8' for text.
    • json.dumps/loads work on strings, json.dump/load on files; CSV values come back as strings.
    • Use logging with levels for diagnostics and print for user-facing output.

    What is the difference between <code>json.load</code> and <code>json.loads</code>?

    The s stands for string. load() takes an open file; loads() takes JSON text already in memory. The same pattern applies to dump and dumps.

    from err links the new exception to the original (available as __cause__) and shows both in the traceback, showing a deliberate translation of a low-level error.

    Module 6

    Modules, packages and environments

    Split code across files, understand how imports are found, and isolate each project's tools in a virtual environment.

    About 55 minutes

    A 40-line script fits in one file. A 4,000-line program does not. Python's answer is simple: a file is a module, a folder of modules is a package, and you pull code from one into another with import. Alongside this, every project needs its own set of installed libraries, kept apart from other projects: that is what a virtual environment is for.

    1. Modules and the different ways to import

    Any file that ends in .py is a module, and its name is the file name without the extension. The standard library is full of modules (math, json, pathlib). The first time you import a module, Python runs its code once and keeps the result in memory, so importing it again elsewhere is instant and shares the same objects.

    2. How Python finds modules

    When you write import tools, Python searches, in order: modules already imported (the cache sys.modules), built-in modules, then each folder listed in sys.path. That list starts with the folder of the script you ran, followed by your installed packages. If nothing matches, you get ModuleNotFoundError: No module named 'tools'. The usual causes are a typo, running the script from the wrong folder, or a library you have not installed in the active environment.

    3. if __name__ == "__main__"

    A file can be both a module (imported by others) and a program (run directly). Python sets __name__ to "__main__" when a file is run directly, and to the module's own name when it is imported. Putting your starting code under if __name__ == "__main__": means importing the file has no side effects.

    Let us prove all of this by building a real package on the fly inside a temporary folder, importing it and watching what happens.

    4. Packages and project layout

    A package is a folder with an __init__.py file (it can be empty). Inside it you can nest more modules and sub-packages and import with dots: from cafekit.pricing import add_tax. Inside a package, a leading dot means "from this same package": from .pricing import add_tax. A tidy layout for a small project looks like this:

    5. Circular imports and how to avoid them

    A circular import happens when a.py imports b.py while b.py imports a.py. Python starts loading a, pauses at the import, starts loading b, which asks for something from a that has not been defined yet, and fails with ImportError: cannot import name 'x' from partially initialized module 'a' (most likely due to a circular import).

    • Move the shared code into a third module that both import (the cleanest fix).
    • Import the module, not the name (import a instead of from a import x) and use a.x only inside functions, after loading has finished.
    • Import inside the function that needs it, as a last resort.
    • Rethink the design: two modules that need each other are usually one module in disguise.

    6. Virtual environments

    Imagine project A needs library version 1 and project B needs version 2. If both install into one global place, one project breaks. A virtual environment is a private folder holding its own Python interpreter link and its own installed packages. Activate it, and python and pip refer to that copy. Nothing you install affects other projects or your system Python.

    You can ask Python which environment you are in. When a virtual environment is active, sys.prefix points inside it and differs from sys.base_prefix.

    7. requirements.txt, pip and pyproject.toml

    pip freeze > requirements.txt records exactly what is installed, with versions, so a teammate (or a server) can recreate the same setup with pip install -r requirements.txt. Pin versions with == (requests==2.32.3) for repeatable builds, or use a looser range such as requests>=2.31,<3 for libraries. Modern projects describe themselves in a pyproject.toml file, a standard configuration file that holds the project name, version, Python requirement and dependencies, and that build and test tools also read.

    8. pipx: installing command-line tools

    Some Python packages are not libraries you import but programs you run (formatters, linters, project generators). pipx installs each such tool into its own hidden virtual environment and puts the command on your PATH, so tools never conflict with your projects: pipx install black then just run black . anywhere. Use pip inside a venv for libraries your code imports, and pipx for stand-alone tools.

    Mistakes beginners make here
    Naming your file the same as a library (a file called random.py or json.py will be imported instead of the real one and cause baffling errors); installing packages with the environment not activated; committing the .venv folder to git (list it in .gitignore; share requirements.txt instead); and forgetting __init__.py (modern Python can import folders without it, but tools and clarity both prefer it).
    Why environments are non-negotiable
    "It works on my machine" is almost always a mismatch of installed versions. A venv plus a requirements file turns your project into something anyone can rebuild in two commands.

    Remember this

    • A module is a .py file; a package is a folder with __init__.py; import runs a module once and caches it.
    • Python searches sys.modules, built-ins, then sys.path (starting with the script's folder).
    • Guard script-only code with if __name__ == '__main__' so imports have no side effects.
    • Break circular imports by moving shared code into a third module.
    • Create one venv per project with python -m venv .venv, activate it, and use python -m pip.
    • Record dependencies in requirements.txt or pyproject.toml; use pipx for stand-alone command-line tools.

    A tour of the standard library

    Python ships with batteries included: learn collections, datetime, re, random, os/sys, functools and argparse before reaching for a package.

    About 60 minutes

    Python's slogan is "batteries included". The standard library is the large set of modules that installs with Python itself: no pip install needed, always available, well tested and documented. Before you write a helper function or add a dependency, spend thirty seconds asking whether the standard library already does it. This module tours the pieces you will use most. The goal is not to memorise everything but to know what exists, so you can look it up.

    1. collections: smarter containers

    The built-in list, dict and tuple cover most needs. collections adds four specialised versions that remove a lot of boilerplate.

    ToolUse it when you want toReplaces
    Countercount how often things appeara dict plus if key in d checks
    defaultdictgroup items; missing keys start with a defaultd.setdefault(...) or if key not in d
    dequeadd/remove quickly at both ends (queues)list.pop(0), which is slow
    namedtuplea light record with named fieldsplain tuples with magic indexes

    2. datetime: dates, times and durations

    Dates look simple until you meet month lengths, leap years and time zones. The datetime module gives you four main types: date (a calendar day), time, datetime (both) and timedelta (a length of time). Subtracting two dates gives a timedelta; adding a timedelta to a date gives a new date. Use strftime to format and strptime to parse using codes such as %d (day), %m (month), %Y (4-digit year), %H:%M (24-hour time).

    Naive vs aware datetimes
    A datetime without a time zone is "naive". Comparing or subtracting a naive and an aware datetime raises TypeError: can't subtract offset-naive and offset-aware datetimes. Pick one style for the whole program, preferably aware datetimes in UTC.

    3. re: regular expressions, the basics

    A regular expression (regex) is a tiny language for describing text patterns. Use it for validating or extracting text that follows a shape: phone numbers, dates in logs, order IDs. Always write patterns as raw strings (r"...") so backslashes reach the regex engine untouched.

    PatternMeaningExample match

    4. random: controlled chance

    random produces pseudo-random numbers: they look random but follow a formula started from a seed. Setting the seed makes a run repeatable, which is valuable for tests and demos. Never use random for passwords or security tokens; use the secrets module for that.

    5. os, sys and platform details

    os talks to the operating system: environment variables, the current folder, listing files. sys talks to the Python interpreter: the version, the command-line arguments (sys.argv) and how to exit. For file paths, prefer pathlib; for configuration such as secrets and API keys, prefer environment variables over hard-coding values in source files.

    6. functools: tools for functions

    functools has three tools worth knowing now. lru_cache remembers results so an expensive function with the same inputs runs only once (memoisation). partial pre-fills some arguments of a function to make a simpler one. reduce folds a sequence into a single value. Also, wraps is used when you write decorators so your wrapped function keeps its name and docstring.

    7. argparse: command-line programs

    Instead of editing the script every time you want a different input, let users pass options on the command line, like python cafe.py add latte --qty 2. argparse defines the arguments, converts types, shows --help automatically and prints a clear error when something is wrong. Normally parse_args() reads sys.argv; passing a list is a handy way to test it.

    Why learn the standard library first
    Standard-library code is installed everywhere, works on every operating system, rarely breaks between versions and is understood by every Python developer. Every dependency you add is something you must update, secure and explain. Reach for the standard library first and a package second.
    How to explore any module
    In a Python shell try import re, then dir(re) to list what it offers and help(re.sub) to read how a function works. The official docs at docs.python.org have a module index and short examples for each module.

    Remember this

    • Counter counts, defaultdict groups, deque makes fast queues, namedtuple makes light records.
    • datetime subtraction gives a timedelta; use strptime/strftime for text, and avoid mixing naive and aware datetimes.
    • Write regex as raw strings, check re.search results for None, and use named groups for readability.
    • Seed random.Random(seed) for repeatable runs; use secrets for anything security-related.
    • Keep secrets in environment variables read with os.environ.get, not in source code.
    • functools.lru_cache, partial and wraps solve common function problems; argparse builds command-line tools with free --help.

    Module 8

    APIs and data with NumPy and pandas

    Fetch data from web APIs, turn JSON and CSV into Python objects, then analyse numbers quickly with NumPy and pandas.

    About 55 minutes

    Most useful programs do not invent their own data. They ask another program for it: today's weather, a cricket score, a payment status, a list of books. The standard way for programs to talk to each other over the internet is an API (application programming interface). In this module you will call a web API, read the JSON that comes back, load tabular data from CSV files, and then use NumPy and pandas to analyse it. These are the same steps behind almost every data and AI project.

    1. What an HTTP API really is

    A web API is a conversation in two parts. Your program sends a request to a URL. The server sends back a response. A request has a method (GET to read data, POST to create it, PUT or PATCH to change it, DELETE to remove it), a URL, optional query parameters after the ?, and optional headers such as your login token. A response has a status code, headers and a body. The body is usually JSON, a text format that looks like Python dictionaries and lists.

    Status codeMeaningWhat your program should do
    200OK, here is your dataread the body
    201Created (after a POST)read the new item from the body
    400Bad request: you sent something invalidfix the parameters; do not retry blindly
    401 / 403Not logged in / not allowedcheck your API key or permissions
    404That item does not existhandle it as 'not found'
    429Too many requests (rate limit)wait, then try again more slowly
    500 and aboveThe server has a problemretry later; it is not your bug

    Python's standard library can make requests, but almost everyone uses the third-party package requests because it is far easier to read. Install it inside your virtual environment with pip install requests. The examples below call a made-up cafe API at api.example.com, so the output is shown as it would appear when the server answers.

    Walk through it line by line. requests.get(...) sends the request and waits for the reply. timeout=5 tells it to give up after five seconds instead of waiting forever. response.status_code is the number from the table above. response.json() converts the JSON text into a Python dictionary, so data["items"] is a list of dictionaries and you can loop over it like any other list.

    Requests without a timeout can hang forever
    By default requests has no timeout. If the server stops answering, your program freezes with no error message. Always pass timeout=. Also remember that a 404 or 500 does not raise an exception by itself: requests.get returns normally and you must check the status.

    2. Handling failure properly

    Networks fail: Wi-Fi drops, servers restart, you pass a wrong ID. Wrap the call in try/except and use response.raise_for_status(), which turns any 4xx or 5xx status into an HTTPError. Catch the specific problems you can handle and let unknown bugs crash loudly.

    Why raise_for_status() exists
    A server replying 404 Not Found is a perfectly successful conversation, so the network library does not treat it as an error. raise_for_status() lets you opt in to treating bad statuses as exceptions, so the same try/except pattern you already know handles them. Many APIs also enforce rate limits: if you get 429, read the Retry-After header, wait that many seconds, and slow down.

    3. Turning JSON text into Python objects

    JSON maps neatly onto Python: objects become dict, arrays become list, strings become str, numbers become int or float, true/false become True/False and null becomes None. response.json() does this for web responses. For text you already have, use json.loads (load string) and json.dumps to go back. Real responses are often nested, so use .get() with a default when a key might be missing.

    4. Tables from text: the csv module

    A CSV (comma-separated values) file is the simplest table format: one row per line, columns separated by commas. Spreadsheets export it and APIs often provide it. Use csv.DictReader, which reads each row as a dictionary keyed by the header row, so your code uses column names instead of fragile positions. Everything arrives as a string, so convert numbers yourself. The demo reads from an in-memory text with io.StringIO; with a real file you would write open("expenses.csv", newline="", encoding="utf-8") instead.

    5. NumPy: fast maths on whole arrays

    A Python list can hold anything, which makes it flexible but slow for maths. NumPy (pip install numpy) provides the array: a grid of numbers that all share one type and live in a compact block of memory. The big idea is vectorisation: instead of writing a loop, you apply an operation to the whole array at once, and NumPy runs the loop in fast compiled code. Comparisons give an array of True/False called a mask, and indexing with a mask filters the data.

    6. pandas: spreadsheets in code

    pandas (pip install pandas) builds on NumPy and adds the DataFrame: a table with named columns and an index, like a spreadsheet you control with code. The five moves you will use constantly are: read_csv to load, head to peek, a boolean filter to select rows, a new column from arithmetic, and groupby to summarise by category. describe() gives instant statistics for a numeric column.

    Common data mistakes
    • df[df["runs"] >= 50 and df["balls"] < 60] fails with ValueError: The truth value of a Series is ambiguous. Use &, | with brackets: df[(df["runs"] >= 50) & (df["balls"] < 60)].
    • Typing a column name wrongly gives KeyError: 'Runs'. Names are case sensitive; print df.columns to check.
    • Looping over rows with for is slow. Prefer column arithmetic, filters and groupby.
    Where to go next with data
    Add matplotlib or plotly for charts, df.to_csv("out.csv", index=False) to save results, and pd.read_json(url) to load an API response straight into a DataFrame. Every step in this module chains together: API call, JSON, DataFrame, summary, chart.

    Remember this

    • An API request has a method, URL, parameters and headers; the response has a status code and usually a JSON body.
    • Always pass timeout= to requests, call raise_for_status(), and catch specific exceptions such as Timeout and HTTPError.
    • Keep API keys in environment variables, never in your source code or Git history.
    • json.loads turns text into dicts and lists; use .get() for keys that may be missing.
    • csv.DictReader gives rows as dictionaries, but every value is a string until you convert it.
    • NumPy applies maths to whole arrays at once; pandas adds named columns, filters and groupby for table-shaped data.

    Module 9

    Testing and debugging

    Read tracebacks calmly, find bugs with logging and the debugger, and write automated tests that tell you when code breaks.

    About 55 minutes

    Every programmer writes bugs. What separates a beginner from a confident developer is not writing fewer bugs, it is finding them quickly and making sure they never come back. This module gives you both skills: a method for debugging, and automated tests that check your code every time you change it. You will also learn the Git basics that let you experiment safely.

    1. Reading a traceback

    When Python crashes it prints a traceback: the chain of function calls that led to the error. Beginners often panic and read it from the top. Read it from the bottom instead. The last line names the exception type and the message. The line above it shows exactly which line of code failed. Everything above that is the path Python took to get there.

    The bug is not really in average. It is a missing decision: what should happen when there are no marks? The traceback tells you where Python noticed the problem. You still have to work out why the data was like that. Always ask: what value did I expect here, and what value did I get?

    Error you seeUsual causeFirst thing to check
    NameErrorTypo or variable used before it existsSpelling and the order of your lines
    TypeErrorWrong kind of value, e.g. "5" + 3Print type(value)
    KeyErrorDictionary key is missingPrint the dictionary's keys
    IndexErrorList position is too largePrint len(your_list)
    AttributeErrorObject has no such method, often NoneWhich variable is None?

    2. A method for finding bugs

    1. Reproduce it. Find the smallest input that makes the bug happen every time.
    2. Read the error from the bottom up and note the file and line.
    3. Form a guess about what is wrong: "I think marks is empty here."
    4. Test the guess by printing, logging or using the debugger. Do not just change code and hope.
    5. Fix it, then add a test so the same bug cannot return unnoticed.
    Why guessing without checking wastes hours
    Changing code at random can hide a bug or add new ones. Each time you test a guess you either confirm it or rule it out, so you always make progress. This is the scientific method applied to code.

    3. print, logging and the debugger

    print is the quickest way to look inside a program, and it is fine for a five-minute bug. Its weakness is that you must delete every print afterwards, and it cannot be turned down or sent to a file. The logging module solves this. Each message has a level (DEBUG, INFO, WARNING, ERROR, CRITICAL), and you choose which levels appear without touching the code.

    Sometimes you need to stop the program and look around. That is what a debugger does. Write breakpoint() on the line where you want to pause, run the script normally, and Python opens the pdb prompt right there. VS Code also lets you click beside a line number to set a breakpoint and use the Debug button.

    Do not leave breakpoints or debug prints behind
    A forgotten breakpoint() freezes your program for whoever runs it next. Before you commit code, search it for breakpoint and stray print calls. Setting the environment variable PYTHONBREAKPOINT=0 makes Python ignore every breakpoint if one slips through.

    4. assert: checking your own assumptions

    An assert statement says "this must be true here". If it is false, Python raises AssertionError immediately and stops, close to the real mistake instead of ten lines later. Use asserts for things that would be your bug if wrong, such as internal rules. Do not use them to check user input, because Python can run with asserts switched off (python -O).

    5. Automated tests: the test-driven mindset

    Debugging by hand is slow, and it only checks what you thought to try today. An automated test is a small function that calls your code with known input and checks the result. You run all tests in seconds after every change, so you find out immediately if something broke. Good tests follow Arrange, Act, Assert: set up the data, call the code, check the outcome.

    Test-driven development (TDD) flips the order: write a failing test first, write the smallest code that makes it pass, then tidy up. Even if you do not follow it strictly, thinking "how would I test this?" before you write a function usually gives you smaller, clearer functions.

    Python ships with unittest in the standard library. Each test is a method whose name starts with test, and you check results with methods such as assertEqual and assertRaises.

    Look at what these four tests cover: a normal case, a case with a discount, an edge case (empty cart) and an error case (bad discount). Edge and error cases are where most real bugs live, so test them on purpose.

    6. pytest: less typing, better messages

    Most professional Python projects use the third-party tool pytest (pip install pytest). You write plain functions and plain assert statements, and pytest rewrites the assertion so a failure shows exactly what each side contained. It also provides fixtures (reusable setup code) and parametrize (run one test with many inputs).

    When a test fails, pytest shows you what went wrong. Suppose someone changed the discount formula by mistake:

    What makes a good test
    Keep each test small (one idea), independent (no test depends on another running first) and fast. Name tests like sentences: test_empty_cart_is_zero tells you what broke without opening the file. When you fix a bug, write the test that would have caught it first, watch it fail, then fix the code.

    7. Git basics: a safety net for experiments

    Git records snapshots of your project, called commits, so you can go back if an experiment goes wrong and work on ideas without disturbing working code. Think of a commit as a save point in a game, with a message that explains what changed. A branch is a separate line of work: you try a risky change on a branch and merge it back only when the tests pass.

    Common testing and Git mistakes
    • Testing only the happy path. Add empty, zero, negative and very large inputs.
    • Tests that print instead of asserting. A test with no assert can never fail, so it proves nothing.
    • Committing everything with the message "update". Write messages that say what changed and why.
    • Committing secrets such as API keys. Once pushed, treat them as leaked and replace them.

    Remember this

    • Read tracebacks from the bottom: error type and message first, then the failing line, then the call path.
    • Reproduce, guess, test the guess, fix, then add a test. Never change code at random.
    • Use logging with levels for anything you want to keep, and breakpoint() to inspect a program mid-run.
    • Write tests as Arrange, Act, Assert, and always cover edge cases and error cases.
    • pytest fixtures and parametrize remove repeated setup and repeated tests.
    • Commit small, branch for experiments, and merge only when the tests pass.
